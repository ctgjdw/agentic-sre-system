# OpenSRE MVP — Plan 4: FIS Chaos + End-to-End Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the two AWS Fault Injection Service (FIS) experiment templates that produce real degradation on the SUT, fire the alarms from Plan 3, and trigger the `opensre investigate` → built-in Telegram messaging chain from Plan 2 — closing the loop on the spec §11 success criterion. End state: `./scripts/start_chaos.sh cpu` and `./scripts/start_chaos.sh rds` each produce an RCA in the configured Telegram group within ~3 minutes.

**Architecture:** Two `aws_fis_experiment_template` resources, `cpu-stress-ecs` (`aws:ecs:task-cpu-stress`) and `rds-reboot` (`aws:rds:reboot-db-instances`), plus a single FIS service role granting the action-specific permissions per spec §4. The CPU-stress action targets ECS tasks tagged `Project=opensre-demo` (which requires us to enable tag propagation in Plan 1's `aws_ecs_service.sut` — done in Task 1 of this plan). The RDS-reboot action targets the demo RDS instance by ARN. A bash wrapper `scripts/start_chaos.sh` accepts `cpu` or `rds`, looks up the experiment-template ID via `terraform output`, calls `aws fis start-experiment`, and tail-follows the SSM log group so the operator can watch the RCA propagate.

**Tech Stack:** Terraform 1.9+ AWS provider 5.x · AWS FIS · ECS task tagging · bash · awscli

## Task 2: FIS IAM service role

**Files:**
- Create: `infra/fis.tf` (initial — IAM only; templates added in Task 3)

- [ ] **Step 1: Create `infra/fis.tf`**

```terraform
# AWS FIS service role. Permissions per spec §4 IAM table:
#   - aws:ecs:task-cpu-stress: ECS describe/list, EC2 describe, SSM SendCommand
#     scoped to AWSFIS-Run-CPU-Stress + the SUT container instance, plus list/cancel.
#   - aws:rds:reboot-db-instances: rds:RebootDBInstance + DescribeDBInstances.

data "aws_iam_policy_document" "fis_assume" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["fis.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "fis" {
  name               = "${var.project}-fis"
  assume_role_policy = data.aws_iam_policy_document.fis_assume.json
  tags               = { Name = "${var.project}-fis" }
}

# Inline 1: ECS CPU-stress action permissions.
data "aws_iam_policy_document" "fis_ecs_cpu_stress" {
  statement {
    sid    = "EcsAndEc2Discovery"
    effect = "Allow"
    actions = [
      "ecs:DescribeTasks",
      "ecs:ListTasks",
      "ecs:DescribeContainerInstances",
      "ec2:DescribeInstances",
    ]
    resources = ["*"]
  }
  statement {
    sid     = "SsmCpuStressOnSutHost"
    effect  = "Allow"
    actions = ["ssm:SendCommand"]
    resources = [
      "arn:aws:ssm:${var.region}::document/AWSFIS-Run-CPU-Stress",
      # Allow targeting any EC2 in this account/region — the underlying ECS
      # container instance ARN can change over time as ASGs replace nodes.
      "arn:aws:ec2:${var.region}:${data.aws_caller_identity.current.account_id}:instance/*",
    ]
  }
  statement {
    sid    = "SsmListCancelCommands"
    effect = "Allow"
    actions = [
      "ssm:ListCommands",
      "ssm:CancelCommand",
      "ssm:GetCommandInvocation",
    ]
    resources = ["*"]
  }
}

resource "aws_iam_role_policy" "fis_ecs_cpu_stress" {
  name   = "${var.project}-fis-ecs-cpu-stress"
  role   = aws_iam_role.fis.id
  policy = data.aws_iam_policy_document.fis_ecs_cpu_stress.json
}

# Inline 2: RDS reboot action permissions.
data "aws_iam_policy_document" "fis_rds_reboot" {
  statement {
    sid     = "RdsRebootAndDescribe"
    effect  = "Allow"
    actions = ["rds:RebootDBInstance", "rds:DescribeDBInstances"]
    resources = [
      aws_db_instance.demo.arn,
      "arn:aws:rds:${var.region}:${data.aws_caller_identity.current.account_id}:db:*",
    ]
  }
}

resource "aws_iam_role_policy" "fis_rds_reboot" {
  name   = "${var.project}-fis-rds-reboot"
  role   = aws_iam_role.fis.id
  policy = data.aws_iam_policy_document.fis_rds_reboot.json
}
```

Note: this re-uses `data.aws_caller_identity.current` declared in Plan 3's `infra/lambda.tf`. If you're applying Plan 4 without Plan 3, add it here too:

# CPU stress on the SUT ECS task. Targets tasks tagged Project=opensre-demo,
# which is propagated to tasks via the ECS service (Task 1 of this plan).
# Action duration 3 min, target 90% CPU — guaranteed to breach the 80% alarm.
resource "aws_fis_experiment_template" "cpu_stress" {
  description = "Stress CPU on the SUT ECS task to trigger sut-cpu-saturation alarm"
  role_arn    = aws_iam_role.fis.arn

  stop_condition {
    source = "none"
  }

  target {
    name           = "Tasks"
    resource_type  = "aws:ecs:task"
    selection_mode = "ALL"

    resource_tag {
      key   = "Project"
      value = var.project
    }
  }

  action {
    name        = "stress-cpu"
    action_id   = "aws:ecs:task-cpu-stress"
    description = "Run AWSFIS-Run-CPU-Stress on the SUT task"

    parameter {
      key   = "duration"
      value = "PT3M"
    }
    parameter {
      key   = "percent"
      value = "90"
    }
    parameter {
      key   = "installDependencies"
      value = "True"
    }

    target {
      key   = "Tasks"
      value = "Tasks"
    }
  }

  tags = { Name = "${var.project}-cpu-stress" }

  depends_on = [
    aws_iam_role_policy.fis_ecs_cpu_stress,
    aws_ecs_service.sut, # ensure the service exists so a task is targetable
  ]
}

# RDS reboot. Targets the demo RDS instance by ARN.
resource "aws_fis_experiment_template" "rds_reboot" {
  description = "Reboot the demo RDS instance to trigger sut-db-connection-errors"
  role_arn    = aws_iam_role.fis.arn

  stop_condition {
    source = "none"
  }

  target {
    name           = "DBInstances"
    resource_type  = "aws:rds:db"
    selection_mode = "ALL"

    resource_arns = [aws_db_instance.demo.arn]
  }

  action {
    name        = "reboot"
    action_id   = "aws:rds:reboot-db-instances"
    description = "Reboot the demo RDS"

    parameter {
      key   = "forceFailover"
      value = "false"
    }

    target {
      key   = "DBInstances"
      value = "DBInstances"
    }
  }

  tags = { Name = "${var.project}-rds-reboot" }

  depends_on = [aws_iam_role_policy.fis_rds_reboot]
}

## Task 4: `scripts/start_chaos.sh` wrapper

**Files:**
- Create: `scripts/start_chaos.sh`

- [ ] **Step 1: Create `scripts/start_chaos.sh`**

```bash
#!/usr/bin/env bash
# Start a Plan-4 FIS experiment. Selects the template by name, prints the
# experiment ID, and (optionally) tail-follows the SSM log group so the
# operator can watch the alarm-to-Telegram chain.
#
# Usage:
#   ./scripts/start_chaos.sh cpu                # start cpu-stress, then return
#   ./scripts/start_chaos.sh rds                # start rds-reboot, then return
#   ./scripts/start_chaos.sh cpu --follow       # also tail /aws/ssm/opensre-investigate
#   ./scripts/start_chaos.sh rds --follow

set -euo pipefail

cd "$(dirname "$0")/.."

if [ $# -lt 1 ]; then
  echo "usage: $0 <cpu|rds> [--follow]" >&2
  exit 1
fi

SCENARIO="$1"
FOLLOW=0
if [ "${2:-}" = "--follow" ]; then FOLLOW=1; fi

REGION=$(cd infra && terraform output -raw aws_region)
SSM_LOG=$(cd infra && terraform output -raw opensre_ssm_log_group)

case "$SCENARIO" in
  cpu)
    TEMPLATE_ID=$(cd infra && terraform output -raw fis_cpu_stress_template_id)
    DESCRIPTION="cpu-stress (AWSFIS-Run-CPU-Stress) on opensre-demo-sut tasks"
    ;;
  rds)
    TEMPLATE_ID=$(cd infra && terraform output -raw fis_rds_reboot_template_id)
    DESCRIPTION="rds-reboot of opensre-demo-db"
    ;;
  *)
    echo "unknown scenario: $SCENARIO (expected cpu|rds)" >&2
    exit 1
    ;;
esac

echo "Starting FIS experiment: $DESCRIPTION"
echo "  region:      $REGION"
echo "  template-id: $TEMPLATE_ID"

EXPERIMENT_ID=$(aws fis start-experiment \
  --region "$REGION" \
  --experiment-template-id "$TEMPLATE_ID" \
  --query 'experiment.id' --output text)

echo "  experiment:  $EXPERIMENT_ID"
echo
echo "Watch experiment progress:"
echo "  aws fis get-experiment --region $REGION --id $EXPERIMENT_ID --query 'experiment.state' --output json"
echo
echo "Expected within ~3 minutes:"
echo "  - CW alarm transitions OK -> ALARM"
echo "  - Lambda log /aws/lambda/ingest_alarm shows ssm:SendCommand"
echo "  - SSM log $SSM_LOG shows opensre investigate stdout"
echo "  - RCA arrives in the configured Telegram group"
echo

if [ $FOLLOW -eq 1 ]; then
  echo "Tailing $SSM_LOG (Ctrl-C to stop)..."
  exec aws logs tail "$SSM_LOG" --since 1m --region "$REGION" --follow --format short
fi
```

## Task 5: End-to-end smoke tests — both scenarios

This is the **headline check** for Plan 4 and the entire MVP: each FIS experiment produces a real RCA in the configured Telegram group within ~3 minutes (spec §11).

For each scenario, the verification is:
1. Run `start_chaos.sh <scenario>`.
2. Watch CloudWatch console (or `aws cloudwatch describe-alarms`) — alarm transitions OK → ALARM within ~60–90 s.
3. Check `aws logs tail /aws/lambda/ingest_alarm` — Lambda logs an `ssm:SendCommand sent commandId=...` line within ~5 s of the alarm.
4. Check `aws logs tail /aws/ssm/opensre-investigate` — `opensre investigate` stdout appears within ~30–180 s.
5. Check Telegram — RCA arrives shortly after the investigation completes (OpenSRE's built-in messaging integration posts directly).

## Teardown

To stop incurring cost between demos:

```bash
cd infra
sed -i.bak 's/opensre_host_enabled = true/opensre_host_enabled = false/;s/sut_desired_count = 1/sut_desired_count = 0/' terraform.tfvars
rm -f terraform.tfvars.bak
terraform apply
```

This destroys both EC2 hosts (Plan 1 SUT + Plan 2 OpenSRE) and the dependent Lambda (Plan 3). FIS templates, IAM roles, RDS, and the UI bucket persist (cheap to keep). Re-flip both vars to bring everything back; ECS rolls a fresh task, OpenSRE host re-bootstraps and re-posts a Telegram "hello".

To fully tear down: `terraform destroy` (wipes Plans 1–4).
