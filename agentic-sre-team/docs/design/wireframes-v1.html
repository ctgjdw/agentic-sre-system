Agentic SRE Team - Ops Console Wireframes

Low-fidelity wireframes for the human side of the agentic SRE system: where the on-call engineer watches investigations unfold, verifies evidence, and makes the two decisions that matter. Red numbered markers carry the design rationale for each screen.

v1 - 2026-07-11 status: for review spec: docs/superpowers/specs/2026-07-11-agentic-sre-team-design.md

Design principles

Derived from the reference research: Datadog Bits AI's hypothesis-tree investigations, Google's incident-management guide, and the agentic-UX patterns that survive user testing (progress ledgers, planning visibility, tool-use disclosure, outcome-preview approvals, confidence signaling).

Decisions first, spectating secondThe engineer's job here is two approvals per case, not watching a stream. Anything waiting on a human is always the loudest thing on screen.
Every claim is a receiptNo agent statement appears without a citation that opens the underlying evidence: the exact query, the raw excerpt, and a deep link to Grafana. Trust is verified, not asked for.
Show the reasoning, collapse the noiseThe progress ledger streams what each agent is doing and why, with tool calls collapsed by default. Transparency without forcing anyone to read raw logs.
Approvals preview their outcomeThe approve button states exactly what happens next ("publishes to Telegram, opens runbook drafting"). Never a bare confirm dialog.
The case is the living incident docOne page accumulates the whole record: signals, hypotheses, evidence, artifacts, decisions. Google IMAG's living document, machine-maintained.
Cost and control stay visiblePer-case spend on every row, per-agent budgets on the governance page, and a global pause that is one click away. Autonomy is governed, not assumed.

Primary workflow

One incident, end to end. The engineer touches the flow at the two dashed gates; everything else is observable but hands-off. The same gates are mirrored in Telegram so approval never requires opening the console.

SignalGrafana alert or Telegram report
->
TriageSeverity, dedup, hypotheses seeded. Ack posted to Telegram
->
InvestigateParallel evidence workers: metrics, logs, infra, changes
->
RCA draftCausal chain, mitigation first, citations verified
->
Gate 1: RCA reviewApprove, edit, or reject. UI or Telegram
->
Runbook draftPre-checks, steps, post-checks, rollback
->
Gate 2: Runbook reviewApprove, edit, or reject
->
Publish + closeArtifacts to Telegram, runbook indexed for next time

  • 1Round counter exposes the bounded-loop guarantee: investigations cannot run forever and the human can see where they are.
  • 2Escalate to human halts agent work and parks the case, preserving everything gathered. Recovery routing is a first-class action, not a failure mode.
  • 3Progress ledger: one entry per graph node with model tier and duration. Streaming text appears in place.
  • 4Planning visibility: the fan-out decision (which workers, why) is a ledger entry the human can read before results exist.
  • 5Tool-use disclosure: each tool call is a collapsed one-liner tagged with the evidence ID it produced. Expanding shows args and raw result.
  • 6The live entry states its intent ("checking slow-query patterns for H2"), not just activity. Reasoning transparency over spinners.
  • 7Hypothesis board is the centerpiece, sorted by confidence. This is the "what do we believe right now" view that Bits AI and Traversal converge on.
  • 8Evidence chips on each hypothesis cross-link to the evidence pane; for/against counts make disagreement visible instead of averaged away.
  • 9Refuted hypotheses stay visible (dimmed) with the refuting evidence named. Showing pruned branches is what makes the surviving diagnosis credible.
  • 10Evidence items are receipts: source, timestamp, query, excerpt. The IDs (E1..En) are the same ones the RCA will cite.
  • 11Deep link to Grafana Explore with the exact query pre-filled, so verification is one click, on the operator's own stack.
  • 12The decision bar is always docked, even when empty, so the engineer always knows whether they are needed and when they will be.
  • 13Add context lets a human inject knowledge mid-flight ("we migrated the db last night") which lands as a high-priority signal for the next node.

Review checklist

Verifier: all claims cite evidence; 0 unsupported claims; confidence 0.81 7
Approve Approve with edits 8 Reject Approving publishes this RCA to the ops Telegram group and starts runbook drafting. It does not change any system. 9 reviewer: alex.goh · logged 10
  • 1Verification badge summarizes the citation-check node's result. Clicking lists any claims that failed and how they were repaired.
  • 2Provenance strip: which tier and model drafted it and what it cost. Reproducible-run metadata one click deeper.
  • 3Mitigation before root cause, always the first block (Google IMAG). A reviewer under pressure reads only this and still acts safely.
  • 4Causal chain as the spine of the RCA: each hop cites the evidence that established it. This is the "single causally consistent diagnosis" pattern.
  • 5Rejected alternatives stay in the artifact, so the reviewer sees what was ruled out, not just what won.
  • 6Citation chips are interactive: clicking a chip in the text loads that evidence here, with the raw excerpt and Grafana deep link.
  • 7Confidence is a number with provenance, not a vibe: it links back to the hypothesis board state that produced it.
  • 8Approve with edits opens an inline diff editor; both versions are stored and the diff is attached to the approval record.
  • 9Outcome preview in plain words next to the buttons. States what approval publishes and reassures what it cannot do.
  • 10Reviewer identity shown at the point of decision; the approval is bound to the case in the audit log.

  • 1The ack is immediate and specific: case ID, proposed severity, what happens next. The CL role from Google IMAG, automated.
  • 2Status updates at phase transitions only, never a firehose. Confidence is stated in the message.
  • 3Inline approval mirrors gate 1. Approve is allowed from chat because the citation check already passed and the outcome is publish-only; anything needing scrutiny routes to the console. Identity of the tapper is recorded.

System states

Queue loading
Skeleton rows in the shape of case rows. No spinners.
Empty queue "No active cases. Last case closed 2h ago. Intake is healthy: webhook OK, poller OK, Telegram OK." An empty queue proves the system is alive, not idle.
Stream reconnecting Thin banner on case detail: "Live stream reconnecting - showing last saved state." State is checkpointed, so nothing is lost; the banner says so.
Case parked: needs human Model provider failed after retries or budget cap hit. Case shows the halt reason, everything gathered so far, and a "Resume" action once the human clears it.

Visual direction for implementation

These wireframes are deliberately monochrome. The build phase applies: a dark-first dense theme (cockpit density) with a light theme of equal care; severity as a semantic color scale kept separate from the single interface accent; tabular numerals and a monospace face for all IDs, queries, and metrics; no decorative animation - the only motion is real streaming state. Charts and meters will follow the dataviz system when real telemetry rendering is built.
